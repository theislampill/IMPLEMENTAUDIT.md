Package contents

What ships in the canonical plugin and its standalone compatibility projection.

One atomic package, two generated projections.

IMPLEMENTAUDIT.plugin.zip is the canonical dual-host package. IMPLEMENTAUDIT.skill is a generated, checksummed standalone compatibility artifact, not a second package topology.
Repo docs, tests, fixtures, release ledgers, generated portal output, and local run artifacts remain maintenance material.

Contents

The canonical plugin preserves skills/implementaudit/, .codex-plugin/plugin.json and .claude-plugin/plugin.json host manifests with equal shared package semantics and permitted host-owned extensions, both pointing to ./skills/, Claude marketplace metadata, and generated package/inventory metadata.
It exposes the stable public/default /implementaudit governor plus exactly four child skills: audit-state, audit-assess, maintainer-only audit-implement, and dual-entry audit-andon. A governor derivation loads at most one child; children return bounded cognition, never chain, and own no authority, currentness, mutation, lifecycle, release, closure, or AUDIT_COMPLETE. A direct audit-andon cord-pull returns to its caller and grants no new authority. The governor's references/, templates/, and helper scripts/ remain one shared deterministic substrate.

The standalone IMPLEMENTAUDIT.skill compatibility artifact is generated from the same source and version. It flattens skills/implementaudit/ to archive-root SKILL.md, references/, templates/, and scripts/, carries deterministic internal-procedure projections for the four children, retains package/inventory metadata, and carries no host manifests, nested skills/ tree, or independently discoverable child packages.
Optional /dashboard/ content is in neither projection. Exact members, bytes, and digests belong to the fresh exact-tree build receipt, not this descriptive page.

Script path boundary

Packaged helper invocations should resolve through ${IMPLEMENTAUDIT_SKILL_DIR:-skills/implementaudit}/scripts/<helper>.
Before installed-package use, resolve and export IMPLEMENTAUDIT_SKILL_DIR to the actual loaded skill directory containing SKILL.md, scripts/, references/, and templates/; the :-skills/implementaudit fallback keeps source-checkout commands working.
The repository root, the IMPLEMENTAUDIT.skill archive file, and IMPLEMENTAUDIT_BASE are not helper directories. IMPLEMENTAUDIT_BASE is the run-root base when used.

Helper failure semantics

Helpers are evidence aids, not authority.
If a helper is missing, fails, or cannot run in the host shell, the agent must record that fact, classify whether it blocks the current phase, and use the Markdown/run-folder fallback when possible.

  • Missing optional helper: record absence and continue with manual evidence when the phase can still be verified.
  • Failed required helper: enter stop-the-line handling, inspect cause, and rerun only after a bounded countermeasure.
  • Host incompatibility: hand off with the exact command, error, environment, and next owner action when no safe fallback exists.

Release and package verification scripts live at the repo root; they are maintenance checks, not shipped runtime helpers.

The canonical plugin must preserve the exact five-skill population and the nested skills/implementaudit/ shared substrate. The standalone compatibility projection must flatten the governor tree, project the four internal procedures under internal-procedures/, and must not carry plugin manifests, a nested skills/ directory, or independently discoverable child packages. In particular, legacy archive-local manifest metadata with skills: "./" is deliberately absent from the compatibility artifact; flattening is a generated layout, not a second plugin manifest. Both projections are generated and checked against one package contract and source identity.

Repo-only material

README.md, CHANGELOG.md, fixtures/, tests/, release ledgers, generated portal output, and local run artifacts are repo-side maintenance material unless a future owner decision changes the package boundary.

The marketplace entry at .claude-plugin/marketplace.json is canonical plugin metadata.
Its presence is not evidence that marketplace discovery, installation, or update behavior was verified.

No LICENSE file exists until the owner selects a license and supplies license evidence.

Release maintenance gates

Release checks are repo-maintenance evidence, not permission to publish.

  • package/implementaudit-package.json defines the package identity, exact skill population, host manifests, shared roots, projections, inventories, and separate artifact budgets.
  • build-release-asset.sh builds both deterministic projections and enforces the package contract.
  • install-plugin-from-release.sh proves only isolated staged plugin copy, inventory, update, rollback, and post-readback behavior.
  • The current checksum check is bash scripts/write-release-checksums.sh --check --all dist dist/CHECKSUMS.txt. Do not reuse the legacy single-asset command bash scripts/write-release-checksums.sh --check dist/IMPLEMENTAUDIT.skill dist/CHECKSUMS.txt against the current two-asset manifest.
  • verify-package.sh runs the broad repository validation suite.
  • tests/release-asset-install.test.sh and tests/release-asset-install-claude.test.sh are separate release-gate checks; each proves only the checked Codex or Claude extraction/copy path unless live host load is also verified.
  • check-no-terminal-cap.sh guards terminal-capability overclaims.
  • Identity, release asset, checksum, publication, and provenance gates remain separate owner decisions.

Package boundary

Do not claim a repo-only document or generated portal output shipped in either package projection unless exact artifact readback shows it.
A checksum match checks artifact integrity. A published checksum manifest can support a separately authorized release provenance gate, but it is not a signature, SBOM, marketplace check, native install check, or host-load proof.

Semantic preservation under footprint pressure

A smaller archive does not by itself close a package failure.
When footprint work changes shipped content, an owner, package membership, an installed path, generated/public material, or an evaluator surface, preserve exact before/after package identity and the owner-backed behaviours at risk.

Required runtime, checker, installed, generated, and public consumers must remain reachable and factually consistent.
Exact literals remain exact only when owned by a parser, checker, public promise, canonical event token, or interoperability contract; otherwise factual equivalence, rather than byte identity, is the test.

See skills/implementaudit/references/lean-operating-discipline.md in the source checkout for the full progressive contract.
This guidance does not alter package membership or claim that a later release exists.
