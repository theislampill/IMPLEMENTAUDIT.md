## A concrete composition question

Consider a shared change used by several supported products. An architectural dependency account can identify a consequential interface or data assumption. A product-realization account can identify which configurations actually contain the changed asset. Maintenance analysis can then ask what those consumers require, which observations should remain unchanged, and whether a transition, repair or retirement is feasible. The chain is useful only when its mappings, baseline, observer, time and consumer agree. Three individually useful artifacts do not establish the joint conclusion by their existence. [Historical lineage intakes and composition models](SOURCE_MAP.json).

The reverse information flow needs its own evidence. An observed product failure can expose a missing family constraint; an actual maintenance response can reveal that a view omitted a relevant consumer. Those are produced observations with a receiving role, not an automatic inversion of the first dependency arrow. A direct product check or a small current inventory can be a simpler adequate route. The public [synthesis account](SSS-S.md) explains this composition boundary and the older repository's concrete target examples while keeping the protected accepted r16 model separate.
